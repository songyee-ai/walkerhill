## 진행 표

- 한 칸에는 상태, 날짜, 한 문장만 적는다. 경위는 아래 "작업별 기록"의 그 작업 절에 적는다.
- 계획된 유닛 번호는 회의에서 한꺼번에 정해 올린다. 중간에 생긴 작업은 자기 번호대(분담 표)에서 다음 번호를 쓰고,
  그 작업의 첫 PR 에 줄을 함께 넣는다.
- 상태: 예약 / 진행 중 / 완료 / 보류

| 번호 | 작업 | 담당 | 상태 |
|---|---|---|---|
| T01 | 저장소·협업 규칙 세팅 | songyee-ai | 진행 중, 11-11, 저장소·보호 규칙·자동 검사는 확인했고 팀원 쪽에서 해야 하는 확인 세 가지가 남았다. |
| T02 | PRD·기술 스택 확정 | 전원 | 진행 중, 11-13, PRD 를 확정했고 저장소 반영, 스택 세부 규칙, 데이터 형식 약속이 남았다. |

## 작업별 기록

작업마다 절을 하나 만든다. 자기 작업의 절만 고친다.

### T01 저장소·협업 규칙 세팅

완료 조건
- [x] 규칙 원본, 진행 문서, 구조 문서가 저장소에 있다 (11-11, 깃헙 저장소 파일 목록 확인)
- [x] `main`, `develop` 브랜치가 있고 보호 규칙이 걸려 있다 (11-11, 깃헙 API 로 보호 설정 조회)
- [x] 자동 검사 파일이 정상이다 (11-11, 수동 실행 `gh workflow run check.yml` 이 성공)
- [x] PR 을 열거나 고치면 자동 검사가 저절로 돈다 (11-11, Actions 를 껐다 켠 뒤 PR 1번에서 실행·성공 확인)
- [x] `develop`·`main` 에 들어갈 때 자동 검사가 저절로 돈다 (11-11, PR 1번 병합 뒤 두 브랜치의 실행·성공 확인)
- [x] 충돌 표시가 있는 PR 은 검사가 실패한다 (11-11, 시험 PR 4번에서 "충돌 표시 검사" 단계 실패 확인 후 닫음)
- [x] 문서 없이 파일만 바꾼 PR 은 검사가 실패한다 (11-11, 시험 PR 5번에서 "문서 동반 검사" 단계 실패 확인 후 닫음)
- [x] 비밀값 푸시 차단이 켜져 있다 (11-11, 깃헙 API 로 저장소 설정 조회)
- [x] `main` 푸시를 저장소 관리자로 제한하는 규칙이 걸려 있다 (11-11, 깃헙 API 의 규칙 생성 응답 확인)
- [x] `private/` 에 넣은 파일은 깃에 올라가지 않는다 (11-12, 시험 파일을 넣고 `git check-ignore` 와 `git status` 로 확인)
- [ ] 팀원 계정으로 `main` 에 푸시하면 거절된다 (팀원 계정이 있어야 확인할 수 있다)
- [ ] PR 을 열 때 깃헙 화면에 확인 양식이 뜬다 (양식이 `develop` 에 들어간 뒤 첫 PR 에서 확인)
- [ ] 팀원 3명이 초대를 수락하고 각자 PC 에 저장소를 받았다 (11-12 초대 수락은 3명 모두 깃헙 API 로 확인, 저장소 받기는 미확인)

특이사항: 타입 검사·빌드·DB 규칙은 스택이 정해지지 않아 비워 뒀다 (T02 뒤에 채운다).

### T02 PRD·기술 스택 확정

완료 조건
- [ ] PRD 가 `docs/` 에 있다
- [ ] 기술 스택, DB 유무, 배포 방식이 정해져 `CLAUDE.md` 의 "스택 확정 후 채울 것"이 채워졌다
- [x] 역할 분담 표와 `STRUCTURE.md` 의 폴더 주인 표가 채워졌다 (11-13, 두 표를 채우고 PRD 14절과 담당이 같은지 대조함)
- [x] 일정이 밀릴 때의 처리가 정해졌다 (11-13, 뺄 순서를 두지 않고 잔업으로 끝내기로 정해 위 "일정이 밀리면"에 적음)

특이사항: 폴더 이름은 제안이다. 팀장이 공통 틀을 만들어 합칠 때 확정한다.

경위
- 11-12: 초안을 [PRD.md](PRD.md) 에 썼다. 범위는 호텔 다이닝 8개 업장이다. 회의에서 정할 항목은 PRD 17절에 모았다.
  초안이라 위 완료 조건은 아직 체크하지 않는다.
- 11-12: 2절과 3절을 다듬었다. 가진 자료를 "기본 데이터"로 부르고, 경쟁 업장을 선택지에 넣고, 끝낼 업무를 네 가지 상황의 비교로 잡았다.
  기본 데이터는 실제 매출 자료로 보고 페르소나 규정의 뼈대로 쓴다.
- 11-13: 페르소나는 기본 데이터의 고객군을 뼈대로 두고 라벨로 나누기로 했다. 추가 데이터를 어디서 모을지 PRD 5.2절에 적었다.
- 11-13: 팀이 정한 내용(고객 범위, 스택, LLM, 페르소나 수, 후기 출처, 깊게 모을 업장, 역할, 검토)을 PRD 17절에 반영했다.
  뺄 기능 순서는 두지 않기로 해서 넷째 완료 조건을 그렇게 고쳤다.
- 11-13: 최종 검토를 했다. 설계 논리 검토, 문서 일치와 내부 자료 점검, 기본 데이터와의 대조 세 갈래로 보았다.
  내부 자료를 옮겨 적은 곳은 없었다. 빠져 있던 정의를 채웠다: 기준 기간, 이용 상황, 가중 합산, 페르소나 배분,
  실행 결과를 두는 곳, 떼어 둘 후기의 담당, 보정의 통과 기준. 정한 것은 PRD 17절에 있다.
  실행 결과를 `private/` 아래에만 둔다는 규칙은 `CLAUDE.md` 의 "비밀값과 공개 저장소" 절에도 넣었다.
- 남은 것: 저장소에 올리기, `CLAUDE.md` 의 "스택 확정 후 채울 것" 채우기(Python 버전, 패키지 설치 방식, 기본 모델),
  `STRUCTURE.md` 의 폴더 이름 확정과 "영역 사이의 약속" 채우기(11-13 기한), PRD 17절의 "아직 정할 것".
