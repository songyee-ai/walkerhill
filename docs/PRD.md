## 1. 한 줄 정의

워커힐 호텔 다이닝 8개 업장을 대상으로, 근거를 갖춘 가상 고객(페르소나)이 조건에 따라 어느 업장에서 무엇을 주문하고
얼마를 쓰는지 돌려 보고, 가격·구성·프로모션을 바꾸거나 경쟁 호텔의 조건이 달라졌을 때의 차이를 같은 조건에서 비교하는 시뮬레이터.

## 2. 배경과 풀 문제

- **출발점은 기본 데이터다.** 우리가 이미 가진 자료 `워커힐_구매상세_L5_전체.csv` 를 **기본 데이터**라고 부른다
  (각자 PC 의 `private/` 에만 둔다). 우리가 가진 유일한 내부 정보이며, 이 프로젝트에서는 **워커힐의 실제 매출 자료로 보고**
  진행한다. 가공된 자료라는 점은 팀이 알고 있고, 실제 자료를 받으면 같은 형식으로 바꿔 끼운다.
- **기본 데이터는 "누가, 언제, 어디서, 무엇을, 얼마나"를 알려 준다.** 날짜, 업장, 상품, 고객군, 유형, 성별, 연령별로
  (여기서 "유형"은 기본 데이터의 `페르소나` 열이다. 우리가 규정하는 페르소나와 헷갈리지 않게 이 문서에서는 유형이라고 부른다. 6.1절)
  수량과 결제액이 한 줄씩 들어 있다. 페르소나를 규정하는 뼈대이자 시뮬레이터가 맞춰야 할 기준이다.
- **기본 데이터에 없는 것은 "왜"다.** 왜 그 업장을 골랐는지, 왜 고르지 않았는지, 가격이나 혜택이 바뀌면 어떻게 움직일지,
  다른 호텔과 무엇을 견주었는지는 매출 자료에 남지 않는다. 그래서 가격이나 구성을 바꿨을 때의 반응을 매출 자료만으로는 낼 수 없다.
- **추가 데이터를 모아 라벨을 붙인다.** 공식 정보, 공개 후기, 공개 통계, 경쟁 호텔의 가격·프로모션을 모은다 (5.2절).
  모은 자료 한 건마다 기본 데이터와 같은 분류(업장, 고객군)에 방문 목적, 동행, 이용 상황, 고른 이유, 걸린 점 같은
  라벨을 붙여 기본 데이터와 이어지게 한다.
- **기본 데이터와 라벨을 붙인 데이터를 합쳐 페르소나를 규정한다.** 기본 데이터가 뼈대(누가 얼마나)를, 추가 데이터가
  이유(왜)를 채운다. 기본 데이터의 고객군을 뼈대로 두고 그 안을 라벨로 나눈다 (6절).
- **경쟁 호텔의 가격과 프로모션을 조사해 결과에 반영한다.** 고객은 워커힐 안에서만 고르지 않는다. 경쟁 호텔의
  가격이나 프로모션이 달라지면 시뮬레이터의 결과도 달라질 수 있어야 한다 (7절).
- **과제가 요구하는 방향.** 고객을 나이와 누구와 왔는지로만 나누지 않고, 왜 사는지, 얼마까지 쓰는지, 언제 오는지,
  왜 다시 오는지로 설명해야 한다. 그리고 가격이나 구성을 손대기 전에 고객이 어떻게 반응할지를 미리 견줘 볼 수 있어야 한다.
- **참고한 선행 사례의 교훈.** 성향을 점수 몇 개로 적고 사람이 가중치를 정한 페르소나는, 만들 때 쓰지 않은 자료로 확인해 보면
  "사람들이 많이 가는 곳을 고른다"는 가장 단순한 방법보다 낫지 않았다. 근거가 연결되지 않은 페르소나는 그럴듯해 보여도 맞지 않는다.

그래서 우리는 **실제 자료의 근거에 기반해 페르소나를 규정하고, 그 페르소나로 시뮬레이션을 만든다.**
"페르소나 고도화"는 속성을 늘리는 일이 아니라, 속성마다 근거를 붙이고 떼어 둔 자료로 확인하는 일이다.

흐름: `기본 데이터 + 추가 수집 데이터 → 라벨링 → 페르소나 규정 → 시뮬레이션 (경쟁 업장 포함) → 가중 합산 → 상황별 비교`

## 3. 사용자와 끝낼 업무

| 항목 | 내용 |
|---|---|
| 사용자 | 워커힐 식음(F&B) 상품·프로모션 기획 담당자 |
| 끝낼 업무 | 같은 고객 집단을 여러 상황에 돌려, 어떤 고객이 왜 고르고 왜 안 고르는지와 업장 사이·호텔 사이의 이동을 비교한다 |
| 입력 | 상황(아래 표), 고객 집단(돌릴 페르소나), 방문 조건(이용 상황, 평일·주말, 끼니, 투숙 여부, 인원, 예산) |
| 결과물 | 화면의 비교 보고: 페르소나별 선택 이동과 이유, 업장별 가상 매출 변화, 경쟁 업장으로 나가거나 들어온 선택, 근거와 가정 표시 |

**비교하는 상황** — 우리 쪽 변경과 경쟁 쪽 변경을 한 흐름으로 다룬다.

| 상황 | 뜻 | 담당자가 답을 얻는 질문 |
|---|---|---|
| 기준 | 지금의 가격·구성·프로모션 그대로 | 지금은 누가 어디를 왜 고르는가 |
| 우리 가격·구성 변경 | 우리 업장의 가격이나 메뉴 구성을 바꾼다 | 바꾸면 누가 들어오고 누가 나가는가 |
| 우리 프로모션 | 우리 업장에 혜택이나 묶음을 붙인다 | 혜택이 없어도 올 고객에게 할인만 주는 것은 아닌가 |
| 경쟁 호텔의 변경 | 경쟁 업장이 가격을 내리거나 프로모션을 연다 | 누가 옮겨 가고, 우리는 무엇으로 대응할 수 있는가 |

결과물은 화면에서 보는 비교 보고까지다. 내려받는 문서는 만들지 않는다.

**시연 시나리오 후보 (제안)** — 발표에서 보여 줄 흐름이다. 화면 담당이 11-17 까지 대상 업장과 바꿀 내용을 확정한다.
바꾸는 값은 공개된 가격에서 정한다.

1. 뷔페의 저녁 가격을 올린다. 어느 고객군이 남고, 어느 고객군이 다른 업장이나 경쟁 뷔페로 옮기는지 본다. (우리 가격·구성 변경)
2. 피자 세트에 혜택을 붙인다. 원래 올 고객에게 혜택만 준 것인지, 새로 들어온 선택이 있는지 본다. (우리 프로모션)
3. 경쟁 호텔이 연말 뷔페를 할인한다. 누가 옮겨 가는지, 우리가 가격으로 맞설 때와 혜택으로 맞설 때가 어떻게 다른지 본다. (경쟁 호텔의 변경)

## 4. 범위

**포함** — 호텔 다이닝 8개 업장. 성격과 이용 상황은 업장 데이터 담당이 공식 사이트로 확인해 고친다.

| 업장 | 성격 | 이용 상황 |
|---|---|---|
| 금룡 | 중식 (광동식 모던 컨템포러리) | 식사 |
| 피자힐 | 피자·파스타 (한국형 프리미엄 피자, 나눠 먹는 세트) | 식사, 포장·구매 |
| 더뷔페 | 뷔페 | 식사 |
| 온달 | 한식 (반가·궁중 요리) | 식사 |
| 르파사쥬 | 고메 스토어 (델리·와인·치즈·피자·육가공품) | 포장·구매 |
| 명월관 | 한우 숯불구이 | 식사 |
| 더파빌리온 | 로비 라운지 (디저트·음료) | 디저트·차 |
| 모에기 | 일식 | 식사 |

(11-13, 업장 데이터 담당이 공식 사이트로 확인해 성격을 고쳤다. 이용 상황은 바뀐 것이 없다. 더파빌리온 메뉴판에는 피자·버거 같은 식사 메뉴도 있지만,
식사 업장과 견주지 않도록 이용 상황은 디저트·차로 둔다. 르파사쥬는 피자힐 피자의 포장 판매도 하는데, 기본 데이터에서는 피자힐 포장으로 잡혀 있다)

- **이용 상황**: 방문은 식사, 디저트·차, 포장·구매 가운데 하나다. 같은 이용 상황에 해당하는 업장끼리만 견준다.
  식사하러 온 고객의 후보에 상품 매장이나 라운지가 들어가지 않고, 그 반대도 마찬가지다.
- **단위**: 방문 한 번. 식사 한 끼, 디저트·차 한 번, 포장·구매 한 번이 각각 방문 한 번이다. 하루 여정은 확장 기능이다.
- **고객**: 투숙객과 비투숙 방문객 모두. 투숙 여부는 방문 조건의 한 항목으로 둔다. (다이닝은 식사만 하러 오는 고객이 있다)
- **상품**: 기본 데이터에 있는 상품을 기준으로 한다. 공식 메뉴판은 가격을 확인하고 기본 데이터에 없는 정보(운영 시간, 좌석,
  예약 조건, 파는 달)를 채우는 데 쓴다. 상황에서 새 상품을 넣을 때만 상품을 더한다. (기본 데이터와 견주려면 상품이 같아야 한다)
- **경쟁 업장**: 워커힐 업장마다 고객이 견줄 만한 경쟁 호텔의 업장을 1~2곳 정해 선택지에 넣는다. 공개된 메뉴·가격·프로모션만 쓴다.
- **선택지**: 같은 이용 상황의 워커힐 업장, 그 업장들의 경쟁 업장, 그리고 "이용하지 않음"을 항상 넣는다.

**경쟁 업장은 업장 데이터 담당이 정한다.** 고르는 기준은 아래와 같다. 정한 목록은 업장 정의 파일에 출처와 함께 적는다.

- 이용 상황과 음식 종류가 같다 (중식이면 중식, 뷔페면 뷔페, 라운지 디저트면 라운지 디저트).
- 가격대가 비슷하다.
- 서울에 있는 같은 급의 호텔 안에 있다.
- 메뉴와 가격이 공식 사이트나 기사로 공개돼 있다.
- 후기에서 "견준 곳"으로 실제로 언급된 업장이 있으면 그 업장을 먼저 고른다.

**제외**

- 객실, 레저, 웨딩·연회, 대외사업, 인룸다이닝, 바
- 실시간 예약·재고·내부 시스템 연동
- 프로모션 후보를 시뮬레이터가 만들어 내는 기능
- 실제 매출 예측이나 실제 구매율이라는 주장 (12절)

| 업장 공식 정보 | 워커힐 공식 사이트의 업장별 메뉴판과 운영 안내, 공식 발표 | 메뉴, 가격, 운영 시간, 좌석·룸, 예약 조건, 파는 달, 진행 중인 프로모션 | 쉽다 | 값 + 출처 주소 + 확인일 |
| 달력 | 한국천문연구원 특일 정보 (공공데이터포털). 11-13 에 정함 | 요일, 공휴일(대체공휴일 포함), 연휴 | 쉽다 | 값 + 출처 + 기준 시점 |
| 공개 후기 | 개인 블로그 글, 지도 서비스의 방문자 리뷰, 예약 서비스의 리뷰. 그 밖에도 근거로 쓸 수 있는 공개 리뷰와 자료는 모두 대상이다 | 방문 목적, 동행, 이용 상황, 주문, 고른 이유, 걸린 점, 견준 곳 | 보통. 수집 담당자가 화면의 목록을 표 파일로 받는다 | 요약하고 분류한 결과만. 원문, 닉네임과 작성자 아이디, 출처 주소는 올리지 않는다 |
| 받은 참고 소스의 후기 자료 | 각자 PC 에 받아 둔 참고 소스 (저장소 밖) | 위와 같다 | 쉽다. 받아 둔 것이 있다 (11-13 에 파일이 있는 것만 확인했다. 다이닝에 해당하는 글이 얼마나 되는지는 확인 전이다) | **올리지 않는다.** 요약과 라벨도 `private/` 에만 두고 실행할 때 읽는다 |
| 경쟁 업장 | 경쟁 호텔의 공식 사이트, 가격을 비교한 기사 | 메뉴, 가격, 프로모션 | 보통. 가격을 공개한 업장부터 | 값 + 출처 주소 + 확인일 |
| 공개 통계 | 통계 기관의 외식·관광 통계 | 지출 수준의 범위 | 어렵다. 호텔 다이닝만 따로 나온 통계는 드물다 | 값 + 출처 + 기준 시점. 참고 범위로만 쓴다 |

**후기를 모으는 방식**

- 후기는 수집 담당자가 자기 브라우저에서 업장의 리뷰 화면을 직접 열어 모은다. 화면에 펼친 목록을 수집 도구로 표 파일에 받는다.
  AI 도구는 수집에 쓰지 않는다. 받은 파일을 나누고 라벨을 붙이는 데만 쓴다.
- 지도 서비스의 이용약관은 자동화된 수단으로 게시물을 모으는 것을 금지한다 (11-13 확인. 아래 "수집 첫날 확인할 것").
  후기는 페르소나의 "이유"를 채우는 근거라 이 과제에 꼭 필요하다. 그래서 팀장이 아래를 지키는 조건으로 이 방식을 쓰기로 정했다 (11-13).
  - 받은 파일은 각자 PC 의 `private/` 에만 두고, 이 과제의 페르소나를 만드는 데만 쓴다. 다른 곳에 올리거나 넘기지 않는다.
  - 저장소에는 요약하고 분류한 라벨만 올린다. 후기의 원문, 닉네임과 작성자 아이디, 프로필과 글의 주소는
    코드, 문서, 커밋 메시지, PR 어디에도 적지 않는다.
- 검색 API 같은 자동 수단은 약관 원문에서 수집 용도가 허용되는지 확인한 뒤에만 쓴다.
- 유효한 근거만 쓴다. 협찬이나 광고로 확인된 글, 실제 방문인지 알 수 없는 글은 뺀다.
- 후기 한 건마다 같은 라벨을 붙인다: 업장, 고객군(기본 데이터의 분류), 방문 목적, 동행, 이용 상황, 고른 이유, 걸린 점, 견준 곳, 근거 등급.
  글과 화면에 없는 라벨은 지어내지 않고 비워 둔다. 근거가 되는 라벨이 하나도 없는 후기는 쓰지 않는다 (`FORMATS.md` 4.1절).
- 방문 목적, 동행, 고른 이유, 걸린 점은 **미리 정한 값 목록**에서 고른다. 목록에 없는 값이 필요하면 목록에 먼저 더한 뒤 쓴다.
  값 목록은 페르소나 담당이 관리한다. (자유롭게 적으면 후기끼리, 그리고 페르소나의 답과 견줄 수 없다)
- 받은 파일에는 작성자의 닉네임과 프로필 주소가 들어 있고, 후기의 출처 주소에도 작성자 아이디가 들어 있는 경우가 많다.
  이 값들은 `private/` 의 받은 파일과 후기 목록에만 두고, 저장소에는 후기 번호, 출처 종류(블로그·지도·예약), 게시 연월만 올린다.
  (11-13, 받은 시험 파일의 닉네임·프로필 번호·글 제목·본문 구절을 저장소의 모든 커밋과 PR 의 글에 대조해 겹치는 것이 없음을 확인했다.
  잰 방법은 `PROGRESS.md` 의 실측 기록에 있다. 새 업장의 파일을 받을 때마다 같은 방법으로 다시 확인한다)
- 후기를 먼저 깊게 모을 업장은 **금룡, 피자힐, 더뷔페, 더파빌리온** 네 곳이다. 나머지 네 곳은 그다음에 모은다.
- 한 사람이 이틀에 100 ~ 150건을 목표로 한다 (11-13 에 잡은 추정이다. 첫날 실제 속도를 재서 `PROGRESS.md` 의 실측 기록에 적고 고친다).
- 후기가 잘 모이는 고객군과 거의 모이지 않는 고객군이 있을 것으로 본다 (11-13 추정이다. 수집하면서 확인한다).
  후기가 모이지 않는 고객군은 억지로 채우지 않고 "이유 근거 부족"으로 둔다.

**떼어 둘 후기 (검증용 20%)**

- 후기는 본문을 요약하기 전에 먼저 주소 목록으로 모은다.
- **업장 데이터 담당**이 그 목록에서 20%를 무작위로 뽑아 가져가고, 그 후기의 요약과 라벨을 직접 붙여 보관한다.
- 페르소나 담당은 나머지 80%만 읽는다. 떼어 둔 후기는 페르소나를 다 만든 뒤에 받는다.
  (페르소나를 만드는 사람이 직접 나누면 "보지 않고 만든다"가 지켜지기 어렵다)
- 떼어 둔 후기가 5건에 못 미치는 업장은 "검증 건수 부족"으로 표시하고 일치율을 말하지 않는다.
- 업장 데이터 담당은 워커힐 8개 업장의 공식 정보 정리를 끝낸 뒤(11-17 부터) 나머지 후기의 라벨링도 돕는다.

**수집 첫날 확인할 것**

- [x] 지도·예약 서비스의 리뷰에 방문 목적과 동행이 항목으로 따로 표시되는지 (표시되면 라벨링이 빨라진다)

### 5.3 근거 등급

모든 값에 등급을 붙인다: `내부 매출 자료` / `공식 사실` / `후기에서 관찰` / `설계 가정` / `미확인`.

- `미확인`은 값을 꾸며 넣지 않고 그대로 표시한다. 기본 데이터에서 가격이 확인되지 않은 것으로 표시된 줄도 `미확인`으로 보여 준다.
- 기본 데이터에 없는 속성(인원, 투숙 여부, 일부 업장의 끼니)은 후기에서 왔으면 `후기에서 관찰`, 팀이 정했으면 `설계 가정`이다.

## 6. 페르소나 고도화

### 6.1 무엇으로 규정하나

페르소나는 두 자료를 합쳐 규정한다. 기본 데이터가 뼈대를, 추가 데이터가 이유를 채운다.

| 출처 | 페르소나에 채우는 것 | 근거 등급 |
|---|---|---|
| 기본 데이터 | 고객군, 유형, 성별·연령 구성. 업장별 매출 비중. 상품별 단가와 판매 단위, 팔린 수량. 매출이 몰리는 요일·계절·공휴일 | `내부 매출 자료` |
| 추가 수집 데이터 (라벨) | 방문 목적, 동행, 고른 이유와 고르지 않은 이유, 가격·혜택에 대한 반응, 견주는 경쟁 업장, 재방문 이유 | `공식 사실` / `후기에서 관찰` |
| 팀이 정한 값 | 위 두 자료로 채우지 못한 속성 | `설계 가정` / `미확인` |

**기본 데이터를 읽을 때 지킬 것**

- 한 줄은 거래 한 건이 아니라, 그날 그 상품을 그 고객군이 산 수량의 합이다. 방문이 몇 번이었는지, 한 번에 몇 명이 왔는지는 들어 있지 않다.
- 그래서 방문 한 번의 지출은 "고른 상품의 단가 × 수량"으로 계산한다. 수량은 인원과 판매 단위(1인, 세트, 판, 개 등)의
  환산 규칙으로 정하고, 환산 규칙은 업장 정의 파일에 적는다.
- 매출은 세금을 뺀 금액(기본 데이터의 `순매출`)으로 센다. 고객이 낸 금액(`총결제액`)과 구분한다.
- 성별·연령은 고객군 전체의 구성으로만 쓴다. 업장 사이나 고객군 사이의 성별·연령 비율 차이는 성향의 근거로 쓰지 않는다.
  수량이 적은 줄에서는 비율이 반올림으로 흔들리기 때문이다.
- 기본 데이터의 `페르소나` 열은 이 문서에서 "유형"이라고 부른다. 이 문서의 "페르소나"는 우리가 규정하는 가상 고객이다.

### 6.2 지금과 목표

| 지금 (기본 데이터만) | 목표 |
|---|---|
| 고객군 하나에 유형 하나가 붙어 있다 | 같은 고객군 안에서도 방문 목적, 예산, 고른 이유가 다른 페르소나로 나눈다 |
| 누가 얼마나 샀는지만 있다 | 왜 골랐고 왜 고르지 않았는지를 속성으로 갖는다 |
| 가격이나 구성을 바꿨을 때의 반응이 없다 | 상황이 바뀌면 고객이 후보 중에서 다시 고르고 이유를 남긴다 |
| 워커힐 안의 구매만 있다 | 경쟁 업장과 견주어 고른다 |

### 6.3 페르소나 한 명이 갖는 속성

페르소나의 속성은 실행마다 바뀌지 않는다. 실행마다 달라지는 값(이용 상황, 평일·주말, 끼니, 투숙 여부)은 방문 조건이다 (7절).

- 기본 데이터에서: 고객군, 유형, 성별·연령대, 업장별 매출 비중, 사는 상품과 단가, 방문 시기
- 방문 모습: 방문 목적, 동행 구성과 평소 인원, 주로 오는 이용 상황과 시간대
- 예산: 1인 기준인지 동행 전체 기준인지, 금액 범위
- 기호와 제약: 음식 기호, 못 먹는 것, 분위기·전망·조용함의 중요도, 아이·어르신 동반 요구
- 구매 성향: 가격 민감도, 혜택·프로모션에 대한 반응, 예약 성향, 대기 허용 정도
- 재방문: 다시 오는 이유와 다시 오지 않는 이유
- 고객군 안의 몫 (6.4절)
- 각 속성의 근거 등급과 출처

### 6.4 나누는 단위와 수

기본 데이터의 고객군을 뼈대로 두고, 그 안을 라벨로 나눈다.

- 기본 데이터의 같은 고객군 수치와 바로 견줄 수 있다.
- 후기가 적은 고객군도 기본 데이터의 수치(누가 얼마나)는 남으므로 페르소나가 비지 않는다. 이유만 "이유 근거 부족"으로 표시한다.
- 예: 한 고객군이 후기의 라벨에 따라 "어르신을 모신 행사 방문"과 "아이를 데려온 외식"으로 갈린다.
  두 페르소나는 같은 고객군의 매출 수치를 나눠 갖고, 고른 이유와 걸리는 점이 서로 다르다.

**수와 배분**: 최소 버전은 1명, 확장 단계의 목표는 6명이다. 적어도 4명은 있어야 한다.

- 기본 데이터에서 다이닝 매출 비중이 가장 큰 고객군 두 개는 각각 두 명으로 나눈다.
- 그다음으로 큰 고객군 두 개는 한 명씩 둔다.
- 어느 고객군인지는 페르소나 담당이 기본 데이터에서 확인해 정한다. 저장소에는 고객군 이름만 적고 비중은 적지 않는다.
- 페르소나가 없는 고객군은 시뮬레이션과 대조에서 빠진다. 화면에 "다루지 않은 고객군"으로 표시한다.

**고객군 안의 몫**: 한 고객군을 두 명으로 나눴을 때 두 페르소나가 그 고객군을 얼마씩 대표하는지다.

- 그 고객군의 후기에서 각 페르소나에 해당하는 라벨의 건수 비율로 정한다 (`후기에서 관찰`).
- 후기가 모자라 비율을 낼 수 없으면 반반으로 두고 `설계 가정`으로 표시한다.
- 한 명만 둔 고객군은 몫이 1이다.

### 6.5 보정 — 기준 상황을 기본 데이터에 맞춘다

기준 상황으로 돌린 결과가 기본 데이터와 맞는지 본다. 맞지 않으면 페르소나를 고쳐 다시 돌린다.

- **기준 기간**: 2026년 전체. 일부 달에만 파는 업장과 상품은 파는 달만 들어간다 (7.2절).
- **비교하는 값**: 페르소나가 있는 고객군마다, 워커힐 업장별 매출 비중. 분모는 워커힐 8개 업장의 매출이다.
  경쟁 업장과 "이용하지 않음"은 기본 데이터에 없으므로 비교에서 뺀다.
- **통과 기준**: 페르소나가 있는 고객군마다 아래 두 가지를 모두 만족한다.
  1. 매출 비중이 가장 큰 업장이 기본 데이터와 같다.
  2. 업장별 비중의 차이가 모두 15%p 이내다.
- 통과 기준은 첫 대조(11-17) 뒤 한 번만 고칠 수 있다. 고치면 이유를 `PROGRESS.md` 의 그 작업 절에 적는다.
- 통과하지 못하면 페르소나의 속성과 고객군 안의 몫을 고쳐 다시 돌린다.
- 이것은 맞추는 과정이지 검증이 아니다. 기본 데이터의 값이 페르소나에 들어가므로 맞는 것이 당연하다. 페르소나가 옳은지는 6.6절에서 본다.
- 대조한 수치는 `private/` 의 실행 결과에 남긴다. `PROGRESS.md` 에는 통과 여부와 잰 방법만 적는다 (10절).

### 6.6 검증 — "왜"는 떼어 둔 후기로 확인한다

떼어 둔 후기 한 건의 라벨(고객군, 방문 목적, 동행, 이용 상황)을 조건으로 넣어 그 고객군의 페르소나를 돌리고, 두 가지를 잰다.
그 고객군에 페르소나가 둘이면 후기의 라벨(방문 목적, 동행)이 더 많이 겹치는 쪽을 돌린다. 겹치는 수가 같으면 고객군 안의 몫이 큰 쪽을 돌린다.
후기에 방문 목적이나 동행이 비어 있으면 그 칸은 조건에 넣지 않고, 겹치는 수를 셀 때 겹치지 않는 것으로 센다.

| 재는 것 | 일치로 보는 경우 | 견줄 단순 기준 |
|---|---|---|
| 업장 일치 | 페르소나가 고른 업장이 그 후기의 업장과 같다 | 그 고객군이 같은 이용 상황에서 기본 데이터 매출이 가장 큰 업장을 늘 고른다 |
| 이유 일치 | 페르소나가 적은 이유 라벨과 후기의 "고른 이유" 라벨이 하나 이상 겹친다 | 만드는 데 쓴 후기에서 그 업장에 가장 흔한 이유를 늘 답한다 |

- 결과는 건수와 함께 적는다 (몇 건 가운데 몇 건). 떼어 둔 후기가 5건에 못 미치는 업장은 "검증 건수 부족"이다.
- 통과 기준은 두지 않는다. 건수가 적어 문턱을 정할 근거가 없다. 단순 기준보다 높았는지 낮았는지를 그대로 적고, 낮아도 숨기지 않는다.
- 한계: 후기는 워커힐에 온 사람만 남긴다. 다른 곳을 고른 사람은 검증에 없고, "견준 곳" 라벨로만 엿볼 수 있다.
- `PROGRESS.md` 의 실측 기록에는 건수, 단순 기준보다 높았는지, 잰 날짜와 방법을 적는다.

## 7. 시뮬레이션 방식

### 7.1 실행 한 번

LLM 이 판단하고 규칙이 검사한다. 금액과 조건은 LLM 에 맡기지 않는다. 실행 한 번은 페르소나 한 명이 방문 조건 하나에서 고르는 것이다.

- **방문 조건**: 이용 상황, 평일·주말, 끼니(식사일 때 점심·저녁), 투숙 여부, 인원과 예산. 인원과 예산을 비우면 페르소나의 값을 쓴다.

1. **후보 추리기 (규칙)** — 이용 상황, 운영 시간, 파는 달, 예약 조건, 인원, 예산으로 갈 수 있는 업장과 주문 가능한 상품만 남긴다.
   같은 이용 상황의 워커힐 업장과 그 경쟁 업장이 함께 후보에 들어간다.
2. **고르기 (LLM)** — 페르소나가 후보 안에서 하나를 고르거나 "이용하지 않음"을 고르고, 이유와 근거가 된 속성을 적는다.
   이유는 5.2절의 값 목록에서 고른 라벨과 한 문장으로 적는다.
3. **다시 검사 (규칙)** — LLM 의 답이 후보에 있던 곳인지, 주문한 상품이 그 업장에 있는지, 금액이 가격표와 맞는지 확인한다.
   하나라도 어긋나면 그 실행을 실패로 기록한다.
4. **원장 기록** — 업장, 상품, 수량과 단위, 표시가, 할인, 고객이 낸 금액(세금 포함)과 세금을 뺀 매출, 선택 이유를 한 줄로 남긴다.
   경쟁 업장이나 "이용하지 않음"을 고른 경우는 워커힐 매출이 0인 줄로 남기고 어디로 갔는지 적는다.

### 7.2 집계 — 선택을 업장별 비중과 가상 매출로 바꾸는 방법

페르소나 몇 명이 한 번씩만 고르면 업장별 비중이 0% 아니면 100%가 된다. 그래서 여러 방문 조건에서 돌리고 가중치로 더한다.

1. **방문 조건 묶음**을 미리 정한다. 이용 상황 × 평일·주말을 기본으로 하고, 식사는 점심과 저녁으로 나눈다.
   묶음의 목록은 엔진 담당이 데이터 형식 약속에서 정한다.
2. 페르소나마다, 방문 조건 묶음마다 **한 번씩** 돌린다. (페르소나 6명에 묶음이 8개면 상황 하나에 48번이다)
3. 실행 한 번이 대표하는 크기 = **페르소나의 가중치 × 그 묶음의 비율**.
4. 업장별 가상 매출 = 그 업장을 고른 실행들의 (세금을 뺀 매출 × 대표하는 크기)를 더한 값.
5. 업장별 비중 = 업장별 가상 매출 ÷ 워커힐 8개 업장의 가상 매출 합. 경쟁 업장과 "이용하지 않음"은 분모에 넣지 않고 따로 보여 준다.

**비율과 가중치를 정하는 법**

- **묶음의 비율**: 그 고객군의 기본 데이터 매출이 묶음마다 얼마씩인지로 정한다 (평일·주말, 이용 상황).
  기본 데이터로 나눌 수 없는 것(일부 업장의 점심·저녁)은 팀이 정하고 `설계 가정`으로 표시한다.
- **고객군 배수**: 기준 상황에서 그 고객군의 가상 매출 합이 기본 데이터의 그 고객군 다이닝 매출(기준 기간)과 같아지도록 한 번 정한다.
  다이닝 매출의 범위는 기본 데이터에서 사업부문이 호텔 다이닝인 8개 업장이다 (11-13 에 정함).
- **페르소나의 가중치** = 고객군 배수 × 고객군 안의 몫 (6.4절).
- 가중치와 비율은 기준 상황에서 한 번 정하고 **다른 상황에서도 그대로 쓴다.** 그래야 상황 사이의 차이에 선택이 달라져 생긴 것만 남는다.
- **일부 달에만 파는 업장과 상품**: 그것을 고른 선택은 파는 달의 비율만큼만 그 업장의 것으로 세고, 나머지는 "이용하지 않음"으로 센다.
  철에 따라 다른 곳을 고르는 것은 P2 다.
- 가중치와 비율은 실행할 때 `private/` 의 기본 데이터에서 계산한다. 저장소에는 적지 않는다.

가상 고객을 여러 명 만들어 돌리는 "집단 반복 실행"은 P2 다. P1 까지는 위의 가중 합산만 한다.

### 7.3 다시 돌렸을 때 같아야 하는 것

- LLM 응답은 요청마다 저장한다. **저장된 응답을 재생하면 원장이 똑같이 나와야 한다.** 시연은 저장된 응답으로 한다.
- LLM 을 새로 부른 실행끼리는 결과가 같다고 보장하지 않는다. 새로 불렀는지 재생했는지를 실행 기록에 남긴다.
- 난수는 P2 의 집단 반복 실행에서 가상 고객을 뽑을 때만 쓴다. P1 까지의 엔진에는 난수를 쓰는 곳을 두지 않는다.
- 상황별 비교는 같은 페르소나, 같은 방문 조건 묶음, 같은 가중치로 한다. 상황마다 달라지는 것은 3절의 표에 적은 변경뿐이다.
- LLM 공급자는 설정으로 바꿔 끼울 수 있게 만든다. 엔진은 "후보와 페르소나를 주면 선택과 이유를 돌려받는다"는
  한 가지 형식으로만 LLM 을 부르고, 공급자마다 다른 부분은 그 뒤에 숨긴다 (13절).
  공급자를 바꾸면 같은 형식으로 끝까지 돌아가야 하지만, 결과가 같을 필요는 없다.
- 호출 횟수와 비용의 상한을 설정으로 둔다. 상한에 닿으면 실행을 멈추고 그 사실을 알린다. 키와 상한은 각자 자기 것을 쓴다.

**준비 단계에서 정할 데이터 형식**

- 업장 정의: 이용 상황, 상품과 가격, 판매 단위와 인원의 환산 규칙, 운영 시간, 파는 달, 출처와 확인일. 경쟁 업장도 같은 형식을 쓴다
- 페르소나 정의: 공개 층과 비공개 층 (10절)
- 후기 라벨과 값 목록
- 방문 조건 묶음
- 상황 정의: 대상 업장과 상품, 바꾸는 종류(가격, 구성, 혜택, 경쟁 쪽 변경), 바꾸는 값
- 기본 데이터 집계 파일: 고객군·업장·묶음별 매출 (실행할 때마다 큰 파일을 다시 읽지 않도록 한 번 계산해 `private/` 에 둔다)
- 실행 결과: 소비 원장, 실행 기록, 저장된 LLM 응답

**일정**

- **일정은 미루지 않는다.** 준비, P0, P1 은 기한 안에 끝낸다. 기한 안에 못 끝내면 기능을 빼지 않고 잔업으로 끝낸다.
  그래서 뺄 기능 순서는 두지 않는다. P2 는 P1 을 다 끝낸 뒤 시간이 남을 때만 한다.
- 후기 수집이 가장 오래 걸린다. 8개 업장을 한꺼번에 모으지 않고 금룡, 피자힐, 더뷔페, 더파빌리온 네 곳부터 깊게 모은다.
  나머지 네 곳은 그다음에 모으고, 후기가 모자란 업장은 "이유 근거 부족"으로 표시한다.
- 경쟁 업장은 후기를 모으지 않고 공개된 메뉴·가격·프로모션만 정리한다. 먼저 깊게 모으는 네 곳의 경쟁 업장부터 채운다.

## 9. 화면 (제안)

화면 담당이 만들면서 바꿀 수 있다. 아래에 든 내용이 어딘가에는 보여야 한다.

1. **조건 입력** — 돌릴 페르소나, 방문 조건, 비교할 상황(우리 쪽 변경, 경쟁 쪽 변경).
2. **실행 결과** — 고른 업장과 상품, 금액, 고른 이유, 고르지 않은 업장과 그 이유.
3. **상황별 비교** — 페르소나별 선택 이동, 업장별 가상 매출 변화, 경쟁 업장으로 나가거나 들어온 선택. 다루지 않은 고객군.
4. **근거 보기** — 값과 속성마다 근거 등급, 출처, 확인일. 가중치와 묶음 비율의 근거 등급.

## 10. 지켜야 할 조건

키를 두는 곳과 문서 언어의 규칙은 `CLAUDE.md` 를 따른다. 여기에는 이 프로젝트에서 더 지킬 것만 적는다.

**표시**

- 화면과 결과의 모든 금액에 "가상"임을 표시한다.

**키**

- 키는 각자 발급하고 서로 주고받지 않는다 (13절).

**내부 자료와 공개 저장소**

- 기본 데이터는 내부 자료다. 기본 데이터에서 뽑은 수치(업장별 비중, 금액, 가중치)는 저장소 파일에 적지 않고,
  실행할 때 `private/` 의 기본 데이터에서 계산한다.
- **실행 결과는 `private/` 아래에만 둔다.** 저장된 LLM 응답, 소비 원장, 실행 기록, 기본 데이터 집계 파일, 대조 결과가 모두 해당한다.
  기본 데이터에서 나온 값이 섞여 있기 때문이다. 팀원끼리는 저장소 밖의 경로로 주고받는다.
- 저장소에는 **가상 예시 값**과 그것으로 만든 저장 응답만 둔다. 키나 기본 데이터가 없는 PC 에서도 이것으로 화면이 돌아간다.
  가상 예시 값은 업장 데이터 담당이 기본 데이터와 같은 형식으로, 기본 데이터의 수치를 따오지 않고 임의로 정해 만든다.
- **페르소나 정의는 두 층으로 나눈다.** 공개 층은 저장소에 두고 공개 후기와 공식 정보에서 온 라벨과 이유만 담는다.
  비공개 층은 `private/` 에 두고 기본 데이터에서 계산한 값과 받은 참고 소스의 후기에서 온 근거를 담는다. 실행할 때 합친다.
  받은 참고 소스에서 온 근거는 공개 층에 섞지 않는다.
- `PROGRESS.md` 의 실측 기록, PR 본문, 커밋 메시지에는 통과 여부, 건수, 잰 방법만 적는다. 기본 데이터와 대조한 비중이나 차이의 수치는 적지 않는다.
- 후기의 원문, 작성자 아이디, 출처 주소는 저장소에 올리지 않는다 (5.2절).

## 12. 하지 않는 주장

- 가상 고객 몇 퍼센트가 골랐다는 결과를 실제 고객의 구매율이나 점유율인 것처럼 내놓지 않는다.
- 가상 매출 변화를 실제 매출 증가의 근거로 제시하지 않는다.
- 기준 상황이 기본 데이터와 맞는 것을 예측이 맞았다는 뜻으로 내놓지 않는다. 맞춘 결과다.
- 경쟁 업장으로 가거나 이용하지 않은 선택의 비율은 맞춰 볼 자료가 없다. 그 크기를 사실처럼 내놓지 않고,
  상황 사이에 얼마나 달라졌는지만 본다.
- 여러 번 돌려 같은 결과가 나왔다는 것을 정확도의 근거로 쓰지 않는다.
- LLM 이 적은 호감 표현을 구매 확률의 근거로 쓰지 않는다.

## 16. 용어

- **기본 데이터**: 이미 가진 자료 `워커힐_구매상세_L5_전체.csv`. 우리가 가진 유일한 내부 정보이며 실제 매출 자료로 보고 쓴다.
- **고객군**: 기본 데이터가 고객을 나눈 분류. 페르소나를 나누는 뼈대다.
- **유형**: 기본 데이터의 `페르소나` 열에 든 값. 고객군마다 하나씩 붙어 있다. 이 문서의 "페르소나"와 다른 것이다.
- **페르소나**: 고객군 하나를 라벨로 나눠 근거를 붙여 규정한 가상 고객 한 명.
- **라벨**: 모은 자료 한 건에 붙이는 분류 값. 업장, 고객군, 방문 목적, 동행, 이용 상황, 고른 이유 같은 것. 미리 정한 값 목록에서 고른다.
- **이용 상황**: 방문의 종류. 식사, 디저트·차, 포장·구매 가운데 하나다. 같은 이용 상황의 업장끼리만 견준다.
- **방문 조건**: 실행마다 달라지는 값. 이용 상황, 평일·주말, 끼니, 투숙 여부, 인원과 예산.
- **방문 조건 묶음**: 집계하려고 미리 정해 둔 방문 조건의 조합 목록.
- **상황**: 비교하려고 돌리는 조건 한 벌. 기준, 우리 가격·구성 변경, 우리 프로모션, 경쟁 호텔의 변경 네 가지다.
- **경쟁 업장**: 워커힐 업장 하나와 고객이 견줄 만한 경쟁 호텔의 업장.
- **업장 정의 파일**: 업장 하나의 이용 상황, 상품과 가격, 판매 단위, 운영 정보, 출처를 적은 파일.
- **소비 원장**: 가상 결제를 한 줄씩 적은 기록. 모든 합계가 여기서 나온다.
- **매출**: 세금을 뺀 금액. 기본 데이터의 `순매출`과 같은 기준이다.
- **가중치**: 페르소나 한 명의 실행 한 번이 실제 방문 몇 번을 대표하는지를 나타내는 값 (7.2절).
- **기준 기간**: 시뮬레이터를 맞출 기본 데이터의 기간. 2026년 전체다.
- **보정**: 기준 상황의 결과가 기본 데이터와 맞도록 페르소나를 고치는 일 (6.5절).
- **검증**: 페르소나가 고른 곳과 이유가 떼어 둔 후기와 맞는지 보는 일 (6.6절).
- **떼어 둔 후기**: 페르소나를 만들 때 보지 않고 검증에만 쓰는 후기.
- **실행 결과**: 실행하면 생기는 파일. 저장된 LLM 응답, 소비 원장, 실행 기록, 대조 결과.
