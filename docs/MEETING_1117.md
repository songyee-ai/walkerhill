**3. 지킬 것**

- 의견은 자기가 고른다. LLM 은 설명하고 받아 적는 일만 한다.
- 자기 영역과 먼 항목은 "모르겠음"으로 둬도 된다. 비워 두지 말고 하나를 고른다.
- 내부 자료를 봐야 답할 수 있으면 파일에는 "회의에서 말로 하겠다"라고만 적는다.
- PR 은 답 파일 하나만 바꾼다. 자동 검사가 통과하면 각자 develop 에 합친다 (승인은 필요 없다).
- 팀장은 합쳐진 세 파일을 모아 정하고, 정한 것을 아래 각 안건의 "정한 것" 칸에 적는다. 그 뒤에 `develop` 을 `main` 에 올린다.

## 1부. 회의 안건 네 가지

### ① 팀이 함께 쓸 모델 하나

**무엇을 정하나.** 보정(T18)·검증(T19)·시연에 쓸 OpenAI 모델을 하나 고른다. 이름에 날짜가 붙은 판(예: `gpt-5.4-mini-2026-03-17`)으로 고른다.

**왜 정해야 하나.**
- 날짜가 없는 이름은 OpenAI 가 속의 모델을 바꿀 수 있다. 어제와 오늘 같은 질문에 다른 모델이 답하면 보정이 무너진다.
- 엔진은 받은 답을 저장해 두고 같은 질문이면 다시 묻지 않고 재생한다. 모델이 다르면 서로의 저장된 답을 재생할 수 없다.
  그래서 넷이 같은 모델을 써야 한 사람이 받은 답을 나머지가 키 없이 재생할 수 있다.

**고르는 방법 (추천).**
1. 후보는 둘: 연습에 쓴 작은 모델과, 같은 계열의 큰 모델 하나.
2. 가상 예시 값(`--data sample`)으로 같은 방문 조건을 두 모델에 똑같이 돌린다. 프롬프트는 p2, p2 가 아직이면 p1 이다.
3. 두 가지를 견준다: 검사에서 어긋난 답(`llm_rejected/`)의 수, 이유 문장이 페르소나의 속성에 맞는지(사람이 몇 건 읽는다).

**추천.** 어긋난 답이 0건이고 이유의 질이 비슷하면 **작은 모델**로 고정한다.
호출 하나의 입력이 2만 토큰을 넘어(T104 실측) 보정 때 수백 번 부르면 비용이 빨리 쌓인다. 작은 모델이 어긋나면 큰 모델로 간다.
정하면 보정(T18)이 끝날 때까지 바꾸지 않는다.

**회의 전에 팀장이 할 것.** 팀장의 OpenAI 키가 지출 상한에 닿아 있다 (11-16, `insufficient_quota`). 상한을 올려야 위의 비교를 돌릴 수 있다.

**정한 것:** **큰 모델**로 고정한다 (11-16, 팀장이 세 사람의 답을 모아 정함. 답은 [meeting-1117/](meeting-1117/)).
두 모델의 비교는 하지 않는다. 대신 큰 모델로 프롬프트 p2 를 가상 예시 값에 돌려 어긋난 답이 0건인지만 확인한다.
이유: T19 는 업장뿐 아니라 이유가 맞는지도 재므로 이유 문장의 질이 중요하다 (borigunbbang, wilstein91).
날짜가 붙은 판 이름은 팀장이 지출 상한을 올린 뒤 정해 `.env.example` 과 T103 에 적는다. 정하면 보정(T18)이 끝날 때까지 바꾸지 않는다.

**바꾼 것 (11-17, 팀장이 정함. T114):** OpenAI 가 아니라 **각자의 Claude 구독**으로 부른다. 공급자는 `claude-code`, 모델은 큰 모델 **`claude-opus-5-5`** 하나다.
- 이유: 넷 다 Claude 구독이 있어 키와 호출 비용 없이 바로 부를 수 있다. OpenAI 는 팀장 키가 지출 상한에 닿아 한 번도 부르지 못했다. 큰 모델로 가는 이유(이유 문장의 질)는 그대로다.
- 확인: 팀장 구독으로 `claude-opus-5-5` 를 가상 예시 값의 방문 1건에 불러 실패 없이 끝났다 (프롬프트 p3). 두 모델의 비교는 하지 않았다.
- 설정은 `.env.example` 에 적었다. 정했으니 보정(T18)이 끝날 때까지 바꾸지 않는다. 규칙은 `CLAUDE.md` 의 "스택"에 있다.

### ② 보정·시연 답을 받을 PC

**무엇을 정하나.** 실제 OpenAI 를 불러 답을 받는 PC 를 한 곳으로 정한다. 나머지는 그 답을 받아 재생만 한다.

**왜 한 곳인가.**
- 기본 데이터로 돌리려면 기본 데이터와 OpenAI 키가 둘 다 있어야 한다. 기본 데이터는 각자 PC 에만 있다.
- 넷이 따로 부르면 같은 질문에 답이 넷 생기고 비용도 네 번 든다. 한 곳에서 받으면 모두가 같은 답으로 화면을 본다.
- 받은 답에는 기본 데이터에서 계산한 값이 섞일 수 있어 `private/` 에만 두고, 저장소가 아닌 길로 나눈다 (CLAUDE.md "비밀값과 공개 저장소").

**추천.** **팀장 PC** 에서 받는다. 엔진 담당이라 막히면 바로 고칠 수 있고, 기본 데이터와 키가 둘 다 있다.
받는 때는 ①에서 모델을 정한 직후(11-17)부터 보정 기한(11-19)까지다. 시연 시나리오 셋(T20)의 답도 같은 PC 에서 받는다.

**정한 것:** 추천대로 **팀장 PC** 한 곳에서 받고 나머지는 재생만 한다 (11-16, 팀장이 세 사람의 답을 모아 정함. 답은 [meeting-1117/](meeting-1117/)).
- 팀장은 답을 받으면 "알릴 것"에 받은 판(모델, 프롬프트, 업장 정의)과 전달 시점을 적는다 (wilstein91 요청).
- 페르소나·프롬프트(borigunbbang)나 업장 정의·집계(hojitea-ui)를 고치면 "알릴 것"으로 알려 다시 받는다.
- (11-17, T114) 공급자를 Claude 구독으로 바꾼 뒤에도 그대로다. 위 "왜 한 곳인가"의 "OpenAI 키"는 이제 "Claude 구독의 로그인"으로 읽는다. 답을 받는 데 팀장의 구독 한도를 쓴다. 한 곳에서 받는 이유에 "구독의 사용 한도를 Claude Code 작업과 함께 쓴다"가 더해졌다.

### ③ 기본 데이터의 요약을 OpenAI 로 보낼지

**무엇을 정하나.** 기본 데이터로 돌릴 때 엔진은 페르소나에게 "어느 업장이 많이 팔리는지" 같은 요약을 함께 보낸다.
이 요약을 OpenAI 로 보내도 되는지 정한다.

**지금 어떻게 보내나.** 실제 수치가 아니라 `high`·`mid`·`low` 세 범주로만 보낸다 (`--base-profile bucketed`).
업장·이용 상황 이름은 이미 질문 본문에 들어가 있어 새로 나가는 것이 아니다.

**왜 다시 묻나.** 처음 계획은 Anthropic 이었는데 11-16 에 OpenAI 로 바꿨다. 받는 회사가 바뀌었으니 다시 확인한다.

**확인할 것 두 가지.**
1. 기본 데이터를 준 쪽이 밖의 서비스로 보내는 것을 막지 않았는가.
2. 키 주인(②에서 정한 PC 의 계정)의 OpenAI 데이터 설정. OpenAI 는 API 로 보낸 데이터를 기본으로 학습에 쓰지 않는다고 밝히고 있지만,
   계정의 설정 화면에서 직접 확인한다.

**추천.** 두 가지가 모두 괜찮으면 `bucketed` 로 보낸다. 하나라도 확실하지 않으면 `--base-profile none` 으로 돌린다.
`none` 이면 페르소나가 업장별 많고 적음을 모르고 고르게 되어 보정이 더 어렵지만, 시뮬레이터는 돈다.

**정한 것:** 추천대로 한다 (11-16, 팀장이 세 사람의 답을 모아 정함. 답은 [meeting-1117/](meeting-1117/)). 두 가지를 확인하면 `bucketed`, 하나라도 불확실하면 `none`.
자료를 준 쪽의 조건은 hojitea-ui 가 회의에서 말로 알리고, 키 주인 계정의 데이터 설정은 팀장이 확인한다.

**바꾼 것 (11-17, T114):** 받는 회사가 OpenAI 에서 Anthropic 으로 바뀌어 두 가지를 다시 확인한다. 확인할 때까지는 `--base-profile none` 으로 돌린다.
1. 기본 데이터를 준 쪽이 밖의 서비스(이번에는 Anthropic)로 보내는 것을 막지 않았는가. hojitea-ui 가 확인해 "알릴 것"에 통과 여부만 적는다.
2. 답을 받는 계정(팀장)의 Claude 개인정보 설정에서 "모델 학습에 사용"이 꺼져 있는가. 개인 구독은 Claude Code 로 보낸 것도 이 설정이 켜져 있으면 학습에 쓰이고 5년 보관되며,
   끄면 30일 보관된다 (Anthropic 공식 문서: <https://code.claude.com/docs/en/data-usage>, 11-17 에 확인). OpenAI API 처럼 "기본으로 학습에 쓰지 않는다"가 아니다.

### ④ 계절·날씨를 엔진에 넣을지

**무엇을 정하나.** 간편 시뮬레이터(T202)에는 계절과 날씨를 고르는 칸이 있지만, 엔진이 아직 받지 않아 "아직 반영되지 않음"으로 표시된다.
이번(기능 동결 11-19 전)에 엔진에 넣을지 정한다.

**추천.** **계절은 넣고, 날씨는 이번에 뺀다.**

| | 계절 (`--month`) | 날씨 |
|---|---|---|
| 일의 양 | 작다. 방문 조건의 달 칸(`RunCondition.month`)이 이미 있다 | 크다. 형식(`FORMATS.md` 9절), 엔진, 프롬프트를 함께 바꾼다 |
| 근거 | 기본 데이터와 공식 정보에 달마다 다른 것(연말 특선, 12월 요금)이 있다. 시연 시나리오 셋이 모두 연말이다 | 후기에 날씨 이야기가 거의 없어 `설계 가정` 등급이 된다 |
| 저장된 답 | 질문이 바뀌어 답을 다시 받아야 한다. 다만 ①에서 모델을 정하면 어차피 모두 다시 받으므로 같이 하면 추가 비용이 없다 | 같다 |

**정하면 할 일.**
- 팀장: 엔진과 방문 조건이 달을 받게 한다. ①의 답을 받기 전에 넣는다.
- borigunbbang: 프롬프트에 달의 뜻(연말·성수기 등)을 적는다.
- wilstein91: 날씨 칸은 화면에서 빼거나 "반영되지 않음" 표시를 둔다 (화면 담당이 고른다).

**정한 것:** **계절은 넣고, 날씨는 이번에 빼고, 달별 가격도 이번에는 넣지 않는다** (11-16, 팀장이 세 사람의 답을 모아 정함. 답은 [meeting-1117/](meeting-1117/)).
- 계절: 팀장이 엔진과 방문 조건이 달을 받게 하고, borigunbbang 이 프롬프트에 달의 뜻을 적는다. ①의 답을 받기 전에 넣는다.
- 날씨: 근거가 없어 `설계 가정` 이 되고, 형식·엔진·프롬프트를 함께 바꿔야 하며, 큰 모델로 정해져 호출 수가 곱으로 느는 비용이 무겁다.
  화면의 날씨 칸은 "다음 단계"로 표시하고 발표의 "앞으로 할 것"에서 소개한다 (wilstein91 의 안은 동결 뒤 과제로 남긴다).
- 달별 가격 (hojitea-ui 질문): 기준 실행의 가격은 10~11월 공식 가격이고, 12월 요금은 시연 시나리오가 상황으로 얹는다.
  그래서 기준과 시나리오를 견주면 "12월 요금 인상이 무엇을 바꿨나"가 나온다. 화면과 발표에 "기준 실행의 가격은 10~11월 공식 가격"을 한 줄 적는다.
  달별 가격을 적는 형식은 동결 뒤 과제로 둔다.

## 2부. "알릴 것"에 남은 팀장 질문과 추천안

`PROGRESS.md` 의 "알릴 것"에서 팀장의 답을 기다리는 질문이다. 추천안대로 갈지 회의에서 확인한다.

### 가. 티스토리·트립닷컴 후기에 원문이 없고 AI 가 요약한 칸만 있는 것 (hojitea-ui 질문, T15)
